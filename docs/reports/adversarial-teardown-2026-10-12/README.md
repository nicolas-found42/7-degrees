## Findings and dispositions

### F01 — identical connection option labels

Requirement R02; type demonstrated friction; impact recoverable selection burden; evidence observed HTTP/HTML plus source and regression; confidence limited to this native select workflow. Expected: a user can distinguish same-name identities, based on README identity-selection promise. Actual: `/chain?from=brownde01` contains `<option value="brownde01" selected>Dee Brown</option>` and `<option value="brownde03">Dee Brown</option>`. 39 duplicate names cover 81 identities. Smallest reproduction: start a connection and inspect the two Dee Brown options. Values are distinct; graph identity is not merged.

Strongest counterevidence: search cards already expose different eras and teams, and choosing canonical IDs through URLs/API works. Discriminating probe: inspect actual option labels and use a label-only selection; if the option itself has visible era/ID context the finding fails. Actual labels do not. Jev classifies this as friction (.88), not proven incorrect graph data. Action D01: add era and ID context only to duplicate names, with ID fallback when metadata is absent. Acceptance: all duplicate choices visibly distinct, exact preselection and unique-name labels preserved, hostile metadata escaped, native keyboard submission unchanged. Disposition: **fixed and verified** by E04/E06/E07/E12; required judgment concerns resolved through E13.

### F02 — stable IDs hidden in links

Requirement R02; type confirmed documentation/UI mismatch; impact minor identification burden; evidence source/visible card and regression. README says results show stable IDs; actual card/profile text shows only name, seasons, teams (ID exists in href/API). Smallest reproduction: search Dee Brown and read card text. Counterevidence: IDs can be recovered from URLs; this limits impact but does not fulfill visible output. Discriminating probe: text-only readback of cards/profile; presence of ID text would reject the finding. Action D02: show escaped canonical ID alongside existing context. Acceptance: result cards and profiles visibly display correct IDs. Disposition: **fixed and verified** by failing-before E05, passing E06/E07/E12; required judgment concerns resolved through E13.

### F03 — intermittent verification timeouts with parallel browsers

Requirement R07; type demonstrated verification friction; impact recoverable verification/operational burden, not a proved product navigation defect; evidence actual check logs and discriminating run. Expected: documented full runner completes every journey reliably on this configured host. Actual final parallel matrix failed three journeys on search/load-state/native evidence popup, while baseline parallel had passed and targeted identity journey passed. Smallest operational reproduction: full/browser profile's default parallel matrix in this host; intermittent, not deterministically reproduced each run. Counterevidence: baseline parallel passed, and app pages/evidence are usable in targeted and HTTP probes. Precise cause (resource scheduling, focus, load-event timing) remains unestablished. Discriminating probe changed test concurrency without code/assertion changes: one-thread full run passed all ten checks, including seven browser/canvas scenarios.

Action D08: `--test-threads=1` only in runner browser-matrix argv and corresponding docs/individual command. No scenario or assertion removed; portable tests keep normal parallelism; each app server remains multithreaded. Acceptance: default documented full runner passes all ten checks after the change. Tradeoff: browser suite runs sequentially, losing parallel speed. Disposition: **mitigated and verified** by E12's default full runner; required judgment concerns resolved through E13. This is an operational mitigation, not proof of the underlying timeout cause or a general CI/platform reliability guarantee.
