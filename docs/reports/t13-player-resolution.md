# T13 player-mention resolution — issue #14

The public `resolution::resolve` service retrieves a lexical shortlist through `search::PlayerCatalog`, then uses a server-side Choice and an independent Noul existence judgment in one request. Code copies the selected canonical identity and its context from the supplied catalog. No player, edge or path is generated by the provider. `/api/resolve` exposes the result; `/resolve` renders resolution, clarification, no-match and unavailable states with selectable canonical profile links.

## Shared runtime contract

```rust
pub fn resolve(
    catalog: &search::PlayerCatalog,
    jev: &JevHandle,
    input: &ResolutionInput,
    config: &ResolutionConfig,
) -> Result<ResolutionCall, search::SearchError>;
```

`ResolutionInput` contains `mention: String` and `context: Option<String>`; both are limited to 160 characters. `ResolutionCall` contains `result: ResolutionResult` and an optional per-call `measurement: JevEvaluation`. The browser API serializes only `result`, which includes `status`, optional canonical `player`, candidate/context records, `reason`, `interpretation`, candidate count/truncation, and optional raw semantic probabilities. Status values are `resolved`, `clarification`, `no_match`, and `unavailable`. A unique exact canonical name with no conflicting context uses deterministic lookup without a semantic call. Empty mentions ask for input.

`ResolutionConfig` defaults to 20 candidates (valid range 1–50), Choice probability 0.90, confidence 0.90, margin 0.25, and Noul presence/absence threshold 0.90. These values are provisional, explicitly parameterized for #16 calibration; three successful examples do not establish general accuracy. `PromptVariant::{Baseline, ExplicitIdentity}` changes prompt wording in this shared service. `OptionOrder::{Lexical, Reverse}` reassigns opaque, sorted `candidate_00...` keys to reversed descriptions and candidate state, so the provider-visible meaning/order actually changes despite sorted JSON maps. The local HTTP test verifies the real outbound criteria mapping, both primitive types and explicit `none` option.

The resolver validates exactly one answer of each expected type/ID, complete unique option coverage, finite probabilities/confidence within 0–1, distribution sum within rounding tolerance, selected option membership, and selection of a top-probability option. Invalid or missing responses return lexical candidates, mark semantic status unavailable and preserve deterministic lookup. Input is treated as data in the prompts; rendering HTML-escapes text and URL-encodes canonical IDs.

## Per-call measurements and transport correction

`JevClient::evaluate_measured` and `JevHandle::judge_measured` return `JevEvaluation { outcome, metadata, elapsed_ms }`. Metadata optionally includes actual provider model, request ID, provider, input/output tokens and reported USD cost. Existing `evaluate`/`judge` callers and scripted transports remain compatible; absent values remain unknown. Concurrent local HTTP tests prove receipts stay attached to each call. Metadata and credentials are absent from browser DTOs/HTML.

The independently reported retry defect was reproduced through the approved real HTTP seam: transport EOF followed by HTTP 429 caused three attempts despite the documented one-retry limit. A separate one-second budget test observed 1407.8 ms before correction. The corrected transport permits at most two application attempts across all retry categories and applies one deadline across retries and response reading/parsing. Failures return `Unavailable`; logs contain status summaries without raw provider errors or credential material. Ten transport tests passed after correction, including the exact mixed-failure sequence and total-deadline case.
